# impl-planner APM package

`impl-planner` は、ソフトウェアまたは構成管理ツールのリポジトリ向けの「計画専用」Skill です。
Codex、Claude Code、GitHub Copilot に実装 plan を作らせたいときに使います。実装そのものは行いません。

English: [README.md](README.md)

## この package でできること

- リポジトリの根拠に基づいた Plan.md 形式の実装 plan を作る
- 目的、背景、リポジトリ理解、前提、未確定事項を整理し、タスク規模に応じた milestone に分ける
- 各 milestone に実装方針、理由付きの影響ファイル / module、対象外、受け入れ条件、検証、判断メモ、リスク、rollback を含める
- entrypoint、呼び出し元、設定、テスト、隣接ドキュメントまで影響範囲をたどり、検証方法を既存のリポジトリの流儀に合わせる
- 確認済みの事実、推論、提案、不明点を区別し、既存のアーキテクチャやレイヤリング規約を尊重する
- 詳細な判断が必要な場合は、推奨案と却下した代替案を理由付きで示し、受け入れ条件やリスク対応が実行可能か確認する
- API、UI、非同期処理、migration、security、monorepo、依存更新、構成管理向けの条件付き profile を使える

## 補足

- この Skill は計画専用です。
- ファイル編集、破壊的コマンド、実装開始を促してはいけません。
- 拡張契約を使う plan に独立した読み取り専用の調査・批評がある場合、サブエージェントを利用できれば少なくとも1件を委譲し、利用できなければ意図的な二巡目レビューを行います。小規模または厳密に直列な plan では委譲を必須にしません。
- 詳細説明を求められたら、複数案、推奨案、メリット・デメリット・トレードオフを返します。
- この Skill は日本語と英語の prompt を受け付けます。

## `apm` でインストールする方法

この repository を clone しなくても、PC に Skill をインストールできます。
リポジトリ参照を直接指定して install します。

```bash
apm install withforesight000/impl-planner#3.1.0 --global --target codex
```

事前に内容を確認したい場合は、`--dry-run` を付けます。

```bash
apm install withforesight000/impl-planner#3.1.0 --dry-run --global --target codex
```

他の対応先にも同じ package を入れられます。

```bash
apm install withforesight000/impl-planner#3.1.0 --global --target claude,copilot
```

working copy を持っている場合は、`apm pack --archive` で bundle を作ってから同じ手順で install できます。

## 使い方

**この Skill は、利用するツールの Plan モードで使うことを推奨します。**

新機能、リファクタ、構成管理ツールの変更、設計判断などで「まず plan が欲しい」ときにこの Skill を使います。

最小入力の例:

```text
impl-planner を使って、このタスクの実装 plan を作ってください。

- やりたいこと
  - [何を実現したいか]
- 背景
  - [なぜ必要か / 何が今の問題か]
```

詳細入力の例:

今回の目的や固有の条件を中心に、分かる範囲で記入してください。未記入の項目は適用される指示やリポジトリの慣例で補います。詳しくは下の記入ガイドを参照してください。各項目に「AGENTS.md に従う」と繰り返す必要はありません。

```text
impl-planner を使って実装 plan を作ってください。

- 対象リポジトリ
  - [変更するリポジトリ名と、対象のアプリ・機能・運用対象]
- リポジトリ全体の理解
  - [誰のどんな目的を達成するシステムか]
  - [分かっている主な処理の流れ：入力から処理・保存・出力まで]
- やりたいこと
  - [誰が、どの状況で、何をできるようにしたいか]
- 背景
  - [現在何が起きていて、誰がどのように困っているか]
  - [なぜ今回対応したいか]
- AIが気づきにくいドメイン知識
  - [一般的には妥当に見えても、この業務では困る動作や判断]
  - [通常のルールが当てはまらない条件と、その場合に期待する動作]
  - [既存の仕様が今の形になった業務上の理由]
- 今回やること
  - [目的を達成するために、今回の変更に含める作業や対応範囲]
- 今回やらないこと
  - [関連していても、今回は含めない変更や後回しにする作業]
- AIに詳しく解説・判断してほしいポイント
  - [迷っている判断、比較してほしい選択肢、推奨案と理由を知りたい点]
- 守るべき設計・流儀
  - [維持すべきレイヤーやモジュールの役割分担と、その理由]
  - [合わせるべき既存パターンや共通処理]
  - [避けたい実装方法と、それを避ける理由]
- 影響範囲として見てほしい箇所
  - [関連しそうな画面・処理の入口・呼び出し元・登録処理。パスは分かる範囲で]
  - [関連しそうなテスト・テストデータ・ドキュメント]
- 制約
  - [維持すべき既存の使い方・API・データ形式などの互換性]
  - [許容できる処理時間や負荷。数値は根拠がある場合だけ]
  - [保存・表示してはいけない情報や、守るべき権限の境界]
  - [許容できる停止時間、実行環境、復旧などの運用上の条件]
  - [利用必須または変更できないランタイム・ライブラリと、その理由]
- 受け入れ条件
  - [どの状況・操作で、どんな結果になれば完了と判断できるか]
  - [失敗時や例外時にも守るべき動作・状態]
- 検証方法
  - [受け入れ条件を確認できる既知の build・test・lint・typecheck・e2e コマンド]
  - [手動で再現する状況、操作手順、確認する結果]
- 既知の地雷
  - [過去の似た変更で、どんな条件のときに何が壊れたか]
- 未確定事項
  - [不明：現状が分からず、調査してほしいこと]
  - [未決定：選択肢はあるが、まだ方針を決めていないこと]
```

### 詳細入力の記入ガイド

**すべての項目を埋める必要はありません。** 今回の目的・背景・固有の条件を中心に記入してください。`AGENTS.md`・関連スキル・リポジトリのドキュメントに記載済みの指示を転記したり、各項目に「AGENTS.md に従ってください」と繰り返したりする必要はありません。特に参照してほしいスキルや資料がある場合は、その名前や参照先を明示してください。

未記入の項目は、次の方針で補います。

1. 適用される `AGENTS.md` と関連スキルの指示に従います。
2. 指示で扱われていない事項は、既存コード・テスト・ドキュメントを調査し、既存の動作や慣例に基づいて判断します。
3. それでも不明な場合、影響が小さい事項は妥当な仮定を置いて進め、計画に明記します。目的・範囲・互換性・安全性などの重要な判断を左右する事項は確認します。

未記入は「制約なし」「対象外」を意味しません。入力のためにファイルパス・コマンド・動作・業務ルールを推測で埋める必要はありません。分からないことや未決定のことを既に把握している場合は、`未確定事項` に記入してください。

以下は「注文フォームの保存失敗後の復帰を改善する」という架空のタスクの記入例です。リポジトリ名・業務ルール・制約は説明用であり、実際のタスクの必須要件ではありません。上のコピー用テンプレートは簡潔に保ち、書きにくい項目があるときにこのガイドを参照してください。

| 項目 | 入力すると何がよくなるか | 考えるための問い | 記入例 |
| --- | --- | --- | --- |
| `対象リポジトリ` | 対象とその境界を特定できます。 | どのリポジトリ・アプリ・運用対象を変更しますか？ | 架空の `order-portal` リポジトリにある注文入力用の Web アプリ。 |
| `リポジトリ全体の理解` | システムの目的や処理の流れと変更を結び付けられます。 | 何をするシステムですか？ 分かっている処理の流れは何ですか？ | 担当者がフォームに注文を入力し、Web アプリが API に送って保存する。 |
| `やりたいこと` | 達成したい結果が明確になります。 | 誰が、どの状況で、何をできるようにしたいですか？ | 担当者が、保存に失敗しても注文を入力し直さずに再試行できるようにしたい。 |
| `背景` | 問題と対応の優先度を伝えられます。 | 現在何が起きていて、なぜ困っていますか？ | 保存に失敗するとフォームが消去され、担当者が注文を再入力している。 |
| `AIが気づきにくいドメイン知識` | 業務ルールとその背景を補えます。 | 一般的には妥当に見えても、この業務では困る動作はありますか？ | 同じ内容の注文を意図的に2件作ることがある。内容の一致だけで重複と判断してはいけない。 |
| `今回やること` | 含める作業を明確にできます。 | 今回、どの変更まで含める必要がありますか？ | 失敗時の入力保持、エラー表示、同じ送信を重複登録しない手動再試行。 |
| `今回やらないこと` | 意図しない範囲拡大を防げます。 | 関連していても、今回は後回しにすることは何ですか？ | 自動再試行と、画面を閉じた後の入力復元。 |
| `AIに詳しく解説・判断してほしいポイント` | 比較や説明が必要な判断に集中できます。 | どの判断について、選択肢と推奨案が欲しいですか？ | サーバーでは保存できたが応答が届かなかった場合に、二重登録を防ぐ方法を比較してほしい。 |
| `守るべき設計・流儀` | 既存の実装規約を維持しやすくなります。 | 維持すべき既存パターンと、その理由は何ですか？ | 認証とエラー処理を統一するため、API 呼び出しは既存の共通クライアントに集約する。 |
| `影響範囲として見てほしい箇所` | リポジトリ調査の手掛かりになります。 | 関連しそうな画面・呼び出し元・テスト・ドキュメントはありますか？ | 注文フォーム、共通 API クライアント、注文作成 API、保存関連のテスト。正確なパスは不明。 |
| `制約` | 採用できない解決策を除外できます。 | 互換性・性能・セキュリティ・運用上、守るべき限界は何ですか？ | 既存の API 利用クライアントを壊さない。注文の入力内容をブラウザーのストレージに永続化しない。 |
| `受け入れ条件` | 完了を観測可能にできます。 | 失敗時も含め、どんな結果を確認できれば成功ですか？ | 保存失敗時に入力が残り、エラーが表示される。初回の応答が失われても、再試行による保存は1件だけになる。 |
| `検証方法` | 期待する結果の確かめ方を伝えられます。 | 既知のチェックや手動操作で、どう結果を確認できますか？ | 通信を切って保存し、入力保持とエラーを確認する。保存成功後の応答喪失も再現し、再試行後の登録が1件であることを確認する。テストコマンドは不明。 |
| `既知の地雷` | 過去の失敗を重点的に確認できます。 | 似た変更で、どんな条件のときに何が壊れましたか？ | 過去の再試行対応では、サーバーの保存成功後にクライアントがタイムアウトすると二重登録になった。 |
| `未確定事項` | 不確実なことを決定事項と区別できます。 | 分かっていないことと、まだ決めていないことは何ですか？ | 不明：API が同じ送信の再試行を識別できるか。未決定：再試行待ちを取り消す操作を画面に設けるか。 |

`やりたいこと` は達成したい結果、`今回やること` は含める作業です。`受け入れ条件` は成功した状態、`検証方法` はその確かめ方です。業務ルールはドメイン知識、実装規約は設計・流儀、採用できる解決策の限界は制約に記入します。

## リポジトリ構成

- `apm.yml`: APM package manifest
- `.apm/skills/impl-planner/SKILL.md`: Skill 本体
- `.apm/skills/impl-planner/references/plan-contract.md`: 中核の出力契約
- `.apm/skills/impl-planner/references/extended-plan-contract.md`: 複雑または高リスクな変更用の条件付き契約
- `.apm/skills/impl-planner/references/examples.md`: 例ファイルへの案内
- `.apm/skills/impl-planner/references/mini-example.md`: plan 密度の確認用の短い例
- `.apm/skills/impl-planner/references/prompt-templates.md`: 再利用用のプロンプトテンプレート
- `.apm/skills/impl-planner/references/detail-request.md`: 必要時に読む判断材料提示の構造
- `.apm/skills/impl-planner/references/formatting.md`: 必要時に読む formatting 制約
- `.apm/skills/impl-planner/references/research-and-critique.md`: 条件付きの委譲・critic pass契約
- `.apm/skills/impl-planner/references/*-task-profiles.md`: 条件付きタスク別チェックリスト
- `.apm/skills/impl-planner/references/config-management-profile.md`: 構成管理向けの条件付き profile
- `.apm/skills/impl-planner/references/platform-notes.md`: プラットフォーム別の補足

## 検証方法

リポジトリルートで次を実行します。

```bash
apm audit --file .apm/skills/impl-planner/SKILL.md
apm audit --file apm.yml
apm pack --dry-run
apm pack --archive --dry-run -v
apm install --dry-run --target codex
apm install --dry-run --target claude
apm install --dry-run --target copilot
```

これで Skill とmanifestのメタデータ、各targetへのinstall、パッケージ内容が想定どおりか確認できます。

## 配布方法

- `apm pack` で配布用 bundle を作る
- 生成された artifact を downstream のインストールやリリース自動化に使う
- `apm.yml` と `.apm/skills/impl-planner/` を source of truth として保つ
